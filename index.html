Polymarket: Wallets, Keys, API Access & Withdrawal Controls

A consolidated technical reference on how Polymarket stores funds, authenticates trading, and gates deposits/withdrawals — plus the real-world failure modes people actually hit.

Polygon · chainId 137 Non-custodial core Geo-gated access layer Updated June 2026
Scope & intent. Everything below is publicly documented architecture and policy, drawn from Polymarket's own docs/help center, security press coverage, and community reports. It explains how the system is built — useful for building bots, integrations, recovering your own funds, and hardening your account. It is not a guide to evading geoblocks, KYC, or fraud controls; those exist for sanctions/AML compliance, and circumventing them violates Polymarket's Terms and can get funds frozen.

Overview & scope

Polymarket runs on Polygon (chainId 137) with a deliberately split design: a non-custodial technical core (smart-contract wallets, an off-chain/on-chain order book, key-based auth) wrapped in a gated access layer (web frontend, geoblocking, app-level account state).

The single most important consequence of that split: Polymarket cannot seize the USDC in your on-chain wallet, but it can freeze your access to the UI and to order placement. Restrictions stop you opening positions and using the app; they don't change the fact that your funds ultimately sit in a contract your private key controls.

1. Account & wallet architecture

The core is a two-layer wallet model: a signer (EOA) that you control, and a proxy wallet (smart contract) that actually holds your money.

LayerWhat it isWhat it holds
EOA / SignerAn Externally Owned Account — a normal keypair. Your "master key."Nothing, usually. It only authorizes.
Proxy WalletA smart contract (1-of-1 multisig) deployed on Polygon, owned/controlled by your EOA.All your USDC (ERC-20) and all your positions (ERC-1155 outcome tokens).

When you first interact with Polymarket, a proxy contract is deployed on-chain that is owned by your signer EOA. Your funds sit at the proxy address, not the EOA address. This trips people up constantly: the address you export a private key for is not the address holding the balance.

Two flavors of signer, two factories

  • Magic Link users (email / Google login): Magic Labs provisions a non-custodial EOA behind the scenes — no browser extension. Polymarket deploys a custom proxy contract for these users via its own factory. This is the POLY_PROXY signature type in the API.
  • MetaMask / browser-wallet users: the signer is your MetaMask EOA, and Polymarket uses Gnosis Safe factories, producing a Gnosis-Safe-style proxy. This is the POLY_GNOSIS_SAFE signature type.

Because both factories are deterministic (CREATE2-style), the proxy address is derived deterministically from the signer address — the same EOA always maps to the same proxy. That's how the app and API can compute where your funds are before the contract is even deployed.

Private key management (Magic Link)

  • If you signed up with email/Google, Magic Labs custodies the key material and you authenticate through Magic's UI.
  • You can export the raw EOA private key via Magic's official reveal flow at reveal.magic.link/polymarket.
  • Developers commonly load it as an env var (e.g. .env.local) so a script can sign orders and derive the proxy wallet programmatically. Polymarket publishes reference repos: magic-proxy-builder-example and magic-safe-builder-example.
⚠️ Exporting that key gives full control of the account to anyone holding it. Treat it like a seed phrase — there is no recovery if it leaks, and it bypasses every UI-level protection.

2. CLOB API & authentication

Polymarket's order book is a CLOB (Central Limit Order Book) — orders are signed off-chain and settled on-chain, so trading stays non-custodial. The API at https://clob.polymarket.com uses a two-tier auth model.

L1 — Private key authentication (EIP-712)

Used to create/derive API credentials and to sign orders. You sign an EIP-712 typed-data struct with your EOA private key:

Domain:  name="ClobAuthDomain", version="1", chainId=137
ClobAuth {
  address:   <signing address>
  timestamp: <server timestamp>
  nonce:     <nonce, default 0>
  message:   "This message attests that I control the given wallet"
}

L1 headers: POLY_ADDRESS, POLY_SIGNATURE (the EIP-712 signature), POLY_TIMESTAMP, POLY_NONCE (default 0).

Credential endpoints

  • Create: POST https://clob.polymarket.com/auth/api-key
  • Derive (deterministic re-fetch): GET https://clob.polymarket.com/derive-api-key

Both require L1 headers and return three values: apiKey, secret, passphrase.

L2 — API key authentication (HMAC-SHA256)

Day-to-day operations (cancel/retrieve orders, check balances/allowances, post pre-signed orders) use L2. Here POLY_SIGNATURE is an HMAC-SHA256 of the request keyed by your API secret.

L2 headers (5): POLY_ADDRESS, POLY_SIGNATURE (HMAC), POLY_TIMESTAMP, POLY_API_KEY, POLY_PASSPHRASE.

Key nuance. L2 credentials let you manage orders, but creating an order still requires an L1 signature on the order payload itself. The API key never gets unilateral spend authority — it can't move funds, only manage the order lifecycle. A leaked API key is far less catastrophic than a leaked private key. This is the deliberate security boundary.

"OAuth" on Polymarket

There is no classic OAuth2 third-party authorization flow for trading. What people loosely call "OAuth" is the Magic Link social login (email/Google) — that's OAuth/OIDC into Magic, which then provisions the EOA. App-to-API authorization is the L1→L2 key-derivation scheme above, not OAuth scopes/tokens. SDKs: py-clob-client (Python), rs-clob-client (Rust), plus community wrappers.

3. Deposits & withdrawals

  • Deposits: USDC (USDC.e / native USDC on Polygon) sent to your proxy wallet address. The app also offers cross-chain / onramp bridges that ultimately land USDC in the proxy.
  • Withdrawals: there is no custodial "withdraw" API — a withdrawal is an on-chain transfer of USDC out of your proxy wallet, authorized by your signer. Because it's your contract, you (with the EOA key) can move funds directly on-chain even outside the UI.
  • Positions can't be force-withdrawn mid-market. Outcome tokens (ERC-1155) only convert back to USDC when (a) you sell them on the order book, or (b) the market resolves and you redeem. In close-only jurisdictions or after a restriction, the documented behavior is: hold existing positions until resolution, redeem, then withdraw — withdrawals of resolved USDC are then unrestricted.

4. Geographic restrictions

Order placement (and in some places deposits) is geoblocked to comply with sanctions, AML, and KYC regimes.

Fully blocked (~33 jurisdictions): United States, United Kingdom, France, Germany, Italy, Belgium, Poland, Australia, Brazil, Japan, Singapore, Taiwan, Thailand — plus sanctioned states: Russia, Belarus, Iran, Iraq, Cuba, Syria, North Korea, Lebanon, Libya, Myanmar, Venezuela, Sudan, South Sudan, Somalia, Yemen, Zimbabwe, Central African Republic, Congo, Burundi, Ethiopia, Nicaragua, US Minor Outlying Islands.

Close-only (manage/close existing positions, no new ones): Singapore, Poland, Thailand, Taiwan.

Regional carve-outs: Ontario (no deposit/trade); Crimea, Donetsk, Luhansk in Ukraine; Japan front-end UI restricted.

The landscape is shifting in 2026 — there's a separate regulated US Polymarket path that does require full KYC (government ID, SSN for tax reporting, proof of residency) to trade legally, distinct from the international platform.

5. Fraud prevention & withdrawal controls

  • VPN / location-spoof detection: Polymarket flags known VPN IP ranges and sudden geographic jumps. Hitting a geoblock via VPN violates the ToS and can trigger account suspension and an immediate withdrawal freeze pending investigation.
  • Behavioral AML triggers: rapid deposit→trade→withdraw cycles, large five-figure churns, or seven-figure positions have been documented tripping internal AML thresholds and forcing identity verification even where KYC isn't otherwise mandatory.
  • On-chain monitoring: a Chainalysis-powered stack watches for insider trading, market manipulation, and illicit-fund flows. Because everything settles on Polygon, the full trade/transfer graph is transparent and analyzable.
  • Stated KYC posture: Polymarket has said KYC won't be mandatory on the main international market, but reserves it as a risk-triggered measure — while the US-regulated entity requires it up front.

The throughline: the technical layer (CLOB, proxy wallets, L1/L2 keys) is deliberately non-custodial and transparent — Polymarket can't seize your on-chain funds — but the access layer (frontend, geoblock, app-level account state) is where freezes and restrictions bite.

6. The pUSD migration (April 2026)

This is the single most important recent change and it touches nearly every withdrawal issue below.

On April 28, 2026, Polymarket migrated its collateral token from USDC.e to pUSD ("Polymarket USD") — a Polygon ERC-20 backed 1:1 by USDC, with the backing ratio enforced on-chain. Alongside it they shipped CTF Exchange V2 (new core contracts, simplified orders, fees calculated at execution instead of at order placement, and elimination of nonce/race-condition order failures).

Why it matters for withdrawals: when you cash out, your pUSD is unwrapped/swapped to native USDC through a Uniswap v3 pool (the "Collateral Offramp"). That swap step is now a dependency — and a failure point (see §8a).

Practical fallout:

  • Users had to approve a one-time conversion of their USDC balance to pUSD and authorize the new contracts before trading resumed.
  • Existing limit orders were cancelled during the ~1-hour maintenance window.
  • The 1:1, no-fee conversion means the normal cash-out experience feels unchanged — until the offramp pool runs thin.

8. The most common withdrawal failures (and fixes)

a) "Insufficient liquidity" / large withdrawal fails — the pUSD→USDC offramp

The Uniswap v3 pool that converts pUSD to native USDC can get exhausted, especially for large amounts. Official guidance:

  1. Break it into smaller withdrawals.
  2. Wait for the pool to rebalance and retry.
  3. Withdraw pUSD directly (skips the Uniswap step) — caveat: some exchanges no longer accept pUSD deposits, so you'd need to convert elsewhere.

b) Small test works, large one stalls

Classic report: a small test transfer lands instantly, the big one sits "pending." Causes: the large amount routed over a different rail, a third-party payout processor delay, or security manual review for large withdrawals. Verify destination network support and that the withdrawal moved past the request stage.

c) "Declined" status + balance momentarily reads $0

Usually a display-vs-ledger mismatch, not lost funds. Check your proxy address on Polygonscan to confirm the on-chain balance is intact, then hard-refresh / re-login to resync the UI.

d) Stuck in mempool / gas spike

Polymarket submits the tx for you, but if gas spikes after submission it can stall or fail. For claims (redeeming winnings), you may need native POL/MATIC in the signer to push it through.

e) Wrong network selected

Picking Ethereum when Polygon is available = higher fees, slower, and a frequent "where's my money" panic. Match the destination network to what the receiving exchange expects.

f) Can't withdraw at all — positions not yet realized

The #1 cause of "stuck" withdrawals: the money is in open positions or an unresolved market. Outcome tokens (ERC-1155) only become withdrawable USDC when you sell them or the market resolves and you redeem.

g) "Withdrawal disabled" / KYC prompt

Indicates a compliance/KYC review hold (see §10). Resolve any pending verification in account settings.

9. Deposits & "missing funds" — the recovery toolchain

When funds don't show, Polymarket has dedicated recovery tooling (not widely advertised):

  • recovery.polymarket.com — sign in with your normal login to discover wallets, scan positions, sell, redeem, and sweep USDC to your EOA. Handles funds sent to the wrong chain (Ethereum mainnet, Base, Arbitrum).
  • matic-recovery.polymarket.com — for non-canonical tokens mistakenly sent on Polygon.
  • Deposits should appear in ~10 min; if confirmed on Polygonscan but not credited, the usual culprit is sending to a profile address instead of the deposit-widget address, or the wrong token variant.
Third-party recovery — extreme caution. The open-source 0-don/polymarket-wallet-recovery tool independently discovers EOA/Proxy/Safe wallets, cancels buys (keeps sells), market-sells positions, redeems resolved markets, and sweeps USDC to your EOA. It needs your private key and MATIC for gas, warns about slippage on market-selling, and advises a small test first. Useful if the Polymarket UI is down or you've lost account access — but it requires handing your key to a script, so only run audited code you trust.

10. Account freezes, KYC & compliance holds

  • What triggers a freeze: rapid deposit→withdraw cycling, VPN/location anomalies, large or unusual flows. Funds can be frozen pending investigation.
  • KYC review: government ID + proof of address, typically 24–48 hr. During review (or if you don't provide docs) access can be limited or fully frozen.
  • Jurisdiction shutdowns happen: Polymarket fully suspended French users in Nov 2024 amid a compliance probe, locking them out of positions. ~35 countries/regions are restricted/blocked.
  • The non-custodial nuance: because your USDC ultimately lives in your proxy contract, an app-level freeze stops you using the UI, but the on-chain funds are still controllable with your private key (via direct on-chain interaction or the recovery tools). Access can be frozen even when custody cannot be seized.

11. Private key reality — including the December 2025 hack

Exporting your key (Magic Link / email users)

  1. Go to reveal.magic.link/polymarket while logged in.
  2. Authenticate with the exact same email or Google account.
  3. Export and store the key offline.
  4. Log out of Magic.

Polymarket will never ask for your key. Note this exports the signer EOA key — your funds sit at the derived proxy address, not the EOA (a constant source of "my key shows $0" confusion).

The December 2025 supply-chain breach (~$3M)

Between Dec 22–24, 2025, users on Reddit/X/Discord reported suspicious logins followed by drained balances — no phishing clicked, 2FA enabled, nothing manually approved, funds simply gone. It was traced to a vulnerability in the Magic Labs email-login (third-party auth) provider — a supply-chain attack on the authentication layer, not Polymarket's smart contracts or settlement. Reported losses ranged from community estimates of $30k+ up to ~$3M in press coverage. Polymarket says the flaw was contained/fixed.

The lesson the community took away: social login (email/Google) is convenient but means a third party sits in your security path. The recommended hardening is to export your private key and move to self-custody, or use a direct wallet connection (MetaMask, etc.) rather than email login, so no external auth provider can authorize access to your funds.

Scam patterns to know

  • Never share seed phrase / recovery phrase / private key with anyone or any "balance fix" tool.
  • Real support never DMs you first on X/Twitter, Discord, or Telegram. Unsolicited "Polymarket support" DMs are scams.
  • Avoid third-party "unlock/fix your balance" services — they're the recovery-tool concept weaponized to steal keys.
